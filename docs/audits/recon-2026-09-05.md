## 1. Executive summary

The repository is unusually disciplined about *verification* — dozens of ratchets and census tests, a fail-closed plan linter, a deterministic merge judge, SHA-pinned CI — and unusually undisciplined about *structure*: one 37,508-line file holds 75 command handlers, a 1,947-line closure, and a 23-parameter function, is imported by 397 test files, and costs about a second of compile per test process. The verification culture is real; this audit's own re-verification found the sweeps' reproductions all stand. Three clusters matter most.

1. **The merge gate's staleness discrimination is partly theatre.** The base-side re-run that is supposed to prove a proof *discriminates* head from base materialises only `grep:` blobs into a temp directory, so every `unit test:` proof is re-run in a directory with no `package.json` or `test/`, fails there for that reason, and is graded `discriminates` → `executed_pass` [R-11]. A `grep:` proof whose target is a directory writes `git show`'s tree listing to disk as a *file*, is stale-blind, and poisons sibling proofs with `ENOTDIR` [R-12]. A `|` in a claim — one exists in the plan today — truncates the claim and turns its proof into prose that nothing judges [R-13]. On plan-only diffs the keyword floor is a tautology (the floor tokens are drawn from the criterion itself), so any body matches N/N [R-15]. None of these red anything; each makes a PASS cheaper than it looks. Standing rule 4 ("green checks ≠ evidence") is defeated from inside its own executor.

2. **Two reproduced crash-or-lose-data defects in the control plane.** Concurrent ledger rotation from two processes (the daemon and `rmd serve` share one ledger) silently drops lines appended between the two renames — including `review.posted`, the row the arming gate keys on [R-1, reproduced twice]. One malformed request line (`GET http://[`) kills `rmd serve` outright because `new URL(req.url)` runs before any try/catch and nothing handles `unhandledRejection` [R-2, reproduced]. A third is one pid-reuse away: the keychain-provision lock spins synchronously with no deadline inside the daemon's event loop [R-3].

3. **The per-tick cost curve is quadratic where it needs to be flat.** Every dispatching tick spawns one `git show` per shard (4.3 s for 1,079 shards; a single `git cat-file --batch` does it in 0.2 s), re-projects the plan in O(tasks × ledger lines) (1.1 s), and rebuilds the GitHub gateway so its delta cache is always cold [R-22..R-25]. At 10× shards the plan sync alone exceeds the 60 s poll. For a harness whose goal is *many* repositories, this is the finding that turns from cost into ceiling.

Everything else is debt of the ordinary kind, at scale: five ways to call GitHub (only one is rate-paced) [R-32], 154 `*Deps` interfaces and no composition root [R-33], four incompatible clock signatures [R-34], eight configuration sources with no schema [R-36], a 5,080-line function holding 4,208 lines of untyped client JavaScript beside an `apps/dashboard` that cannot load as shipped [R-35], fixtures copy-pasted across hundreds of test files [R-41], a mutation gate whose trigger list misses four of its own five test files [R-42], and a docs surface that had drifted in six specific, now-corrected places [R-46, R-47, R-52, R-53, R-56].

**The single biggest risk:** R-11/R-12/R-13 together. A harness that merges its own code on the strength of executed proofs must not have an executor whose "discriminates" verdict is reachable without discrimination.
