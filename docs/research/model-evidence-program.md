# Model evidence program: from fleet work to field trials

Status: design, 2026-09-25. No trial result, public data transfer, new routing policy, paid call, or merge gate is authorized by this document. The site's `/field-trials` page initially publishes the method and an explicit no-results state (PORTAL-T29); a chart requires a later reviewed release.

## What we have, and what we do not

`worker.assignment` in `src/lib/worker.ts` records the requested and selected model, provider, effort, routing rule, capacity context, and immutable assignment ID before execution. A terminal verdict may carry `selection_assignment_id`, `served_model`, tokens, `worker_duration_ms`, `total_cost_usd`, and `billing_mode`. `routing-v1` in `src/lib/analytics-route.ts` joins these, exposes bounded aggregates, and counts unjoined assignments and receipts separately. Its display accumulator coalesces some absent token, duration, and cost fields with `?? 0`; those totals are **not** proof of measured zero. A benchmark projection must retain per-field coverage and missingness instead of inheriting that convention.

`src/lib/routing-experiments.ts` reports the live Sol/Sonnet comparison among eligible assignments. Its headroom-selected arm is observational, even when both providers were eligible: provider capacity, time, task mix, and the possibility of a mixed-arm task still confound a causal model comparison. Its task merge rate is useful operationally but not verified completion. `experiment-v1` in `src/lib/operator-agent.ts` already retains hypothesis, baseline, outcome, and rollback history; it is an experiment receipt, not an allocation engine.

`ledger-compact` already preserves exact distinct rows in compressed rotations and has a recoverable cold-store window for superseded archives; the daemon invokes bounded compaction on corpus pressure. `src/lib/gardener.ts` already provides a proposal loop and outcome credit/debit. Neither is a benchmark cohort view. Do not make another raw event lake or let an LLM perform canonical deduplication.

The missing joins are task difficulty and risk at assignment time, run/attempt identity across retries and agent handoffs, pinned prompt/tool/harness/scorer revisions, a declared allocation mechanism, end-to-end verification and follow-up outcomes, and explicit completeness for every cost/time field. An instance on another repo can use different tools and tests, so a model label alone is not the treatment.

## Instrumentation contract: `benchmark-run-v1`

Emit a metadata-only, versioned envelope at assignment, attempt completion, verification, and follow-up milestones. This supplements existing ledger rows and reuses `selection_assignment_id`; it does not rewrite them. An instrumenter must tolerate old rows and expose `unavailable`, not invent historical values. All IDs below are high-cardinality ledger/trace join keys, never metric labels or public rows.

| Field group | Required meaning | Why it matters |
| --- | --- | --- |
| Provenance and rights | instance pseudonym, repo pseudonym, local permission-receipt reference, publication rights (`private`, `aggregate-opt-in`, `public-benchmark`) | Multiple installs can compare internally without publishing a customer's identity. Permission is specific and revocable. |
| Work | run ID, attempt ID, assignment ID, task class, risk band, difficulty rubric revision, cohort/corpus revision | Repeated attempts and unequal task mix cannot masquerade as independent model wins. |
| Working stack | provider; requested model, selected model, served model (nullable with reason); effort; prompt, harness, tool, skill, environment, and scorer revision | A model + harness result is not a model-only result. A fallback is visible. |
| Allocation | experiment ID (if any), randomized versus observational, eligibility snapshot hash, randomization unit and deterministic seed hash, assigned arm, exposure time, crossover/refusal reason | An intention-to-treat analysis must include every eligible assignment, even non-starters and fallbacks. |
| Outcome | worker call result; first-pass verification; verified completion; test/CI/review receipts; fix dispatches; follow-up defect, revert, and censoring window | Merge, green local tests, and live correctness are distinct. |
| Resources | queue, work, tool, test, review, human-wait, and total elapsed time where observed; input/output/cache tokens with source; retries; peak context/compactions | Separates model speed from queue and human delay, and reveals costly repair loops. |
| Accounting | billing mode, cash cost if provider/invoice reported, notional cost if modelled, subscription capacity use, currency and rate-card revision, source and missingness reason for each | `0` cash on a subscription is not zero resource use. Never add cash and notional dollars into one total. |

Represent an outcome as `{state: observed | failed | censored | unavailable, value?, reason?, observedAt?}` where appropriate. Preserve missingness reason for absent receipts, unreadable provider usage, no invoice, pre-instrumentation rows, or an unfinished follow-up window. A failure is not a missing outcome; a task still open at analysis cutoff is censored, not a failure. Record the release's observation window and whether follow-up data were mature. Generate instance/repo pseudonyms from locally held, rotatable material; never publish an unsalted hash of a repository name as if it were anonymous. No raw prompts, source files, credentials, or account labels enter this envelope or a public telemetry pipeline. Keep private identifiers local; a public release is a separate projection with a stricter allowlist.

OpenTelemetry may carry a trace correlation key and low-cardinality task class/model family/status attributes. It is not the durable source of truth. Keep run IDs, task IDs, repository names, and user names out of metric dimensions; put high-cardinality identifiers in local events or traces with governed retention. GenAI content capture is opt-in and is **off** for this program. This follows [OpenTelemetry's GenAI privacy guidance](https://opentelemetry.io/blog/2026/genai-observability/) and its [cardinality failure analysis](https://opentelemetry.io/blog/2026/cardinality-limits-in-opentelemetry/).

## Two-stage gardener: exact consolidation, then interpretation

**Deterministic consolidation** is a local, replayable projection, not an LLM summarizer. Its input is the existing three-form ledger union (`ledger.*.ndjson.gz`, `ledger.*.ndjson`, and `ledger.ndjson`), using the established union reader and dedupe rules. It incrementally joins assignment, attempt, terminal, and follow-up receipts; writes partitioned `benchmark-cohort-v1` snapshots by instance/day/experiment/task class/model + harness revision; and includes source hashes, schema revisions, a watermark, count of rows/bytes read, join coverage, per-field coverage, and explicit unknown/censored counts. Use a bounded batch with an atomic replacement, idempotent on replay. A late receipt or retraction invalidates only the affected cohort and its published candidate; recompute from retained authoritative rows before replacing it. A missing archive or failed read marks the cohort unavailable, never healthy/empty.

Measure bytes per day, events per run, archive compression ratio, cardinality per proposed dimension, snapshot rebuild time, and query latency on real instances before setting operating targets. Retain exact raw rows under `ledger-compact`'s existing policy. Keep compact daily rollups and only consented, content-redacted, sampled trace exemplars; move superseded derived versions to recoverable cold storage until their source lineage and successor have reconciled. Downsample or expire only materialized views that can be rebuilt, with a receipt of what changed. Any resource guard is a visible best-effort backpressure/follow-up task, not a hard ceiling that strands a PR or silently drops the only evidence. Report overflow, source gaps, and unsupported schema versions explicitly. No instance uploads private raw ledger lines to the marketing site.

**Insight gardener** reads these bounded cohorts, not the entire ledger on every tick. It detects drift, high repair or intervention burden, contradictory results, missing joins, and promising model + harness configurations. It emits at most one evidence-linked observation/experiment proposal/follow-up per pass, deduplicates by hypothesis and cohort lineage, and retires proposals invalidated by new data. The existing `gardener.ts` proposal/outcome machinery can score suggestions against later verified outcomes and human corrections; merge alone is not proof that the recommendation helped. A proposal is not a merge gate, PR hold, or silent routing mutation. It may queue a bounded task for a broken instrumenter or an expired release. Promotion of a route remains a separate reviewed policy action with a rollback receipt.

Each instance can keep its private mart locally. A federated public release builder accepts only reviewed, consented aggregate cohorts and emits a static, schema-checked artifact. For opt-out or revocation, withdraw the affected release and invalidate its cache; do not try to subtract a private run from an opaque graph without a lineage record.

## Experiment ladder and measurements

Start with an **A/A** pilot on public fixtures or explicitly opted-in work: allocate equivalent eligible tasks to two labels using the proposed randomization path, while both labels run the same stack. Check sample-ratio mismatch, assignment-to-receipt join rate, missingness by arm, duplicate/crossover handling, metric stability, and whether the analysis would spuriously call a winner. This establishes that the experiment machinery is trustworthy before it ranks models. No paid pilot starts without explicit budget approval.

For A/B trials, pre-register the eligible population, randomization unit (usually task, not retry), seed/strata, pinned corpus and model + harness revisions, primary verified completion outcome, denominator including non-starters, follow-up window, uncertainty method, stopping rule, and quality/privacy/PR-flow guardrails. Keep retries in the original arm for intention-to-treat; report crossover separately. Avoid overlapping trials on one task unless a factorial design is declared. An LLM judge can triage qualitative issues but must be calibrated against human-labeled goldens, show disagreement and abstention, and never silently relabel a failed check as success. Repeated peeking without a declared sequential method does not make a credible winner. Microsoft Research's [trustworthy experimentation guidance](https://www.microsoft.com/en-us/research/articles/patterns-of-trustworthy-experimentation-during-experiment-stage/) specifically calls out data-quality, primary, diagnostic, and guardrail metrics; its [sample-ratio mismatch taxonomy](https://www.microsoft.com/en-us/research/publication/diagnosing-sample-ratio-mismatch-in-online-controlled-experiments-a-taxonomy-and-rules-of-thumb-for-practitioners/) is a useful A/A diagnostic.

Record a human-effort or expert-duration estimate when one is independently available, so performance can be stratified by task length and compared with [METR's task-horizon approach](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/). Do not infer human time from agent runtime. Mark corpus exposure and solution leakage risk by revision: [SWE-rebench's decontamination research](https://arxiv.org/abs/2505.20411) is a warning that familiar public issues can reward recall rather than problem solving. Keep fresh, held-out tasks and later live follow-up separate from the reproducible public corpus; neither tier substitutes for the other.

Priority-ordered trials, after instrumentation passes A/A:

1. **Model × effort on a pinned stack.** Paired public/opt-in tasks, equal tool/prompt/test budgets and task strata; compare verified completion, repair burden, human intervention, all-in elapsed time, tokens, cash and notional cost separately. Varying provider adapters too makes this a model + harness comparison, labeled as such.
2. **Context strategy.** Scoped retrieval/memory versus broad repository context at the same model and tools; measure verified completion, incorrect file edits, context churn, token use, latency, and whether omitted evidence caused a missed defect.
3. **Review and repair.** Independent reviewer versus same-agent review, and earlier targeted verification versus later full preflight; measure escaped defects after follow-up, fix dispatches, reviewer effort, and PR time-to-merge. Never replace the required safety gate with the experimental arm.
4. **Escalation and judge policy.** LLM judge suggesting human escalation versus deterministic baseline on a labeled, replayable corpus; measure missed high-risk escalations, false interruptions, calibration, resolution time, and abstentions. Keep human approval where authority requires it.
5. **Agent topology and tool policy.** Serial versus bounded parallel specialists; tool-call batching; alternate search or test-selection strategies. Measure verified completion per unit elapsed time, merge conflicts, duplicate work, stuck-PR incidence, wasted calls, and handoff loss.
6. **Gardener loop itself.** Shadow-ranked recommendations versus current prioritization, then opt-in canary; measure proposal acceptance, confirmed improvement after deployment, false leads, duplicate tasks, and evidence debt. Do not score the gardener on how many PRs it creates.

The dashboard should show a completion-versus-time/cost frontier, first-pass → repair → verified outcome funnel, A/B lift with uncertainty by task class, and a **coverage/unknown** graph that can worsen without being mistaken for model regression. Task strata and revisions stay visible. Small samples get intervals and an explicit inconclusive state, not a forced ranking. [OpenAI's eval guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices) emphasizes task-specific outcomes and human-calibrated judges; [agent eval guidance](https://developers.openai.com/api/docs/guides/agent-evals) uses traces to diagnose failures and datasets for repeatable tests. The run envelope and release format should not depend on one vendor's hosted eval product.

Three research surfaces can make this distinctive without inventing a leaderboard. A **fitness frontier** plots verified completion against both elapsed time and separately labeled cash/notional cost, with uncertainty and task class visible. A **recovery curve** follows first-pass failure through self-repair, human intervention, and eventual verification, including open/censored work; it rewards an agent that gets unstuck rather than merely drafts quickly. A **measurement-debt map** displays assignment, receipt, score, and follow-up coverage by stack revision, so the audience can see where we refuse to rank models. A paired public "task twin" corpus can then repeat the same permissible issue across model + harness variants and sites while preserving the distinct live-fleet observational tier. These are hypotheses for the A/A and A/B ladder, not measured outcomes today.

## Eval card: `eval-card-v1`

Every trial (the W1-T4575 A/A, the W1-T4603 paid pilot, the W1-T4625 paired trial) carries a versioned eval card built by `buildEvalCard(trial, evidence)` in `src/lib/eval-card.ts` (W1-T4630). The card holds the evidence a reader needs to judge the result's validity. It is not the result.

- **Pre-registration.** The sha256 of the canonical protocol text (line endings and trailing whitespace normalized), when it was committed, and the first assignment time. The card is publishable only when the commit strictly precedes the first assignment. A missing protocol, an unparseable time, a later commit, or a text that no longer matches its registered hash each block publication by name.
- **Design.** Estimand, randomization unit, and a bounded propensity excerpt (`unavailable` when none was declared).
- **A/A and sample ratio.** An A/A trial reports each arm's rate, the difference with a 95% interval, and a two-proportion p-value, and it never declares a winner. Any other trial cites its A/A receipt or reads `missing`. The sample-ratio check is a chi-square goodness of fit of distinct units per arm against the planned allocation, flagged at p < 0.001. A unit counts in the arm of its earliest assignment, and a later assignment to another arm is logged as a crossover.
- **Power.** Units per arm for the declared minimum detectable effect (two-sided two-proportion test, the equation R's `power.prop.test` solves), the power achieved at the smallest observed arm, and McNemar pairs (Connor 1987) when a discordant-pair rate is declared.
- **Coverage.** Each declared `arm|stratum` cell is reported. A cell with no graded outcome reads `unknown` with n = 0, never a zero rate. Censored or unavailable outcomes are counted separately.
- **Grader validity.** From the latest `review.posted` `decision_verdict` per trial task and PR: the share of criteria graded `executed_stale`, `not_executable`, and `exec_error`, plus the share of reviews that graded a holdout criterion. With no graded review it reads `unknown`.
- **Deviations.** Declared deviations and derived ones (late pre-registration, changed protocol, sample-ratio mismatch, crossovers), in time order.

The card is always `visibility: private`. It is served read-scoped at `GET /v1/analytics?projectionVersion=eval-card-v1&trial=<id>`. A trial the daemon has not registered returns an unavailable, unpublishable card. Nothing publishes a card on its own. The site's reviewed release gate is the only consumer that may make one public.

## A/A integrity trial: `benchmark-aa-v1`

`rmd benchmark-aa --trial <manifest.json>` (W1-T4575, `buildBenchmarkAaReport` in `src/lib/benchmark-aa.ts`) is the first rung of the ladder above. It is an operator report, not a gate: it changes no routing, blocks no dispatch, review or merge, and spends nothing.

- **Eligibility.** The `benchmark-aa-trial-v1` manifest names a `public-fixture` cohort, or an `opted-in` one with a consent receipt and a local pseudonym salt. Anything else is refused by name. The manifest pins one stack (provider, model, effort, and immutable harness, prompt, tool, scorer and environment revisions), a strata revision, and the tasks with their class and risk.
- **Allocation.** Each task takes one of two labels by the parity of `sha256(benchmark-aa-allocation-v1, trialId, taskId)`. No run, attempt or spawn enters the draw, so a retry never moves a task. The allocation receipt lists task pseudonyms, labels, the pinned stack and its hash per label, and a receipt hash. A change against a registered or prior hash is reported. Non-starters stay in their arm's denominator, and retries stay in the original arm. A recorded label that disagrees with the draw is a crossover. An exposure off the pinned stack is a fallback. Neither is moved or hidden.
- **Evidence.** The report reads the three-form ledger union and counts files per form. It collapses exact replayed rows and counts them, and honors retractions. Rewritten assignment receipts are counted as conflicts. Unless `--no-cohort` is given, it reconciles the union's assignment count with the `benchmark-cohort-v1` projection. Verified outcomes join through task case files (`--case-files`). An open PR is censored and a missing terminal is a join gap; neither is a failure.
- **Report.** The report shows the sample ratio against 50/50 for allocated and for exposed units, as a chi-square and an exact binomial test (mismatch at p < 0.001). It shows per-arm assignment, terminal and verified joins; missingness of served model, tokens, duration, billing mode and cost; fallbacks, crossovers and strata; outcome maturity; and, through `eval-card-v1`, the observed difference with a 95% interval. API cash estimates, subscription notional cost, a trial-level invoice and unknown cost are reported apart and never summed, and unknown carries reasons, not dollars. A difference at p < 0.05 between identical arms is a `spurious-difference` finding, and a billing-mode split between arms is a `billing-mode-imbalance` finding. The report never declares a winner.
- **Receipt and refresh.** Each run writes one dated private report with a `benchmark-aa-receipt-v1` receipt. The receipt carries hashes, rates, finding kinds and recommended follow-ups, with no task, run, host or assignment identifiers, and W1-T4603 cites it. A later run replays the full union, and rows at or before the prior watermark are reported as late evidence for the arms they touch. A refresh that cannot read a source keeps the last dated report and marks it `stale`. Without a prior it reads `unavailable`, never an empty healthy trial.

## Approved paid pilot: `benchmark-paid-pilot-v1`

The operator approved one paid pilot (#7418): $100 of cash in total, over seven days, across the three opted-in repos (W1-T4603, `src/lib/benchmark-paid-pilot.ts`). Each task in a pre-registered population is randomized to a **paid** arm (an API-billed model) or a **control** arm (a subscription model). Merging the code starts nothing and spends nothing. No daemon cadence, PR check or build starts the pilot.

- **How to activate.** First run `rmd benchmark-aa --trial <manifest.json>` and confirm its report reads `no-integrity-concern-detected`. Then write a `benchmark-paid-pilot-request-v1` file. It names the three consented repos and their consent receipts, a local pseudonym salt, the task assignment seed and eligible population, the paid and control arms pinned to provider, model and effort, the immutable harness, prompt, tool, scorer and environment revisions, a strata revision, `verified-completion` as the primary outcome, a maturity window in days, the protocol text, and the approval reference. Run `rmd benchmark-paid-pilot activate --request <request.json> --aa-report <state>/benchmark-aa-v1.<trial>.json`. Activation refuses by name when the A/A receipt is missing, tampered, older than 24 hours, stale, inconclusive or reports integrity concerns. It also refuses when another pilot is still active, or when this one was already activated.
- **What activation records.** It writes `<state>/benchmark-paid-pilot-v1.<pilot>.protocol.json` once and never overwrites it. The file holds the protocol and a privacy-safe `benchmark-paid-pilot-receipt-v1`: the UTC start and expiry, the $100 aggregate cash ceiling, the repos, the seed and population, the pinned arms with stack hashes, the outcome, the maturity window, the uncertainty method (intention-to-treat difference in verified completion, Wald 95% interval), the stopping rule (one analysis at expiry plus the maturity window, with no interim winner), and the cited A/A receipt.
- **The clock starts at activation.** The seven days run from the activation time, not from approval, filing or build. A second activation refuses and never restarts the clock.
- **Allocation and intention to treat.** Each task takes its arm by the W1-T4575 draw, seeded by the pilot. No run, retry or spawn enters the draw. Non-starters, retries, fallbacks and crossovers stay in the task's original arm and in its denominator.
- **Cash accounting.** Cash counts only distinct API-billed worker-call receipts (`worker.attempt`) for pilot assignments. They are read from the three-form ledger union, from activation on, and a receipt replayed across rotations counts once. The figure is a provider estimate, never an invoice. Subscription notional cost is reported apart and never depletes the ceiling. A missing price is unknown, never zero.
- **What pauses, and what does not.** Only the paid arm pauses, through `paidPilotArmAdmission`. It pauses on missing or ambiguous cost evidence, including a paid call whose receipt has not landed, so paid calls run one at a time. It also pauses on an expired window, a spent budget, allocation drift (a changed protocol, a changed draw, or a recorded label that disagrees with it), or an unreadable, missing or malformed source that the spend window needs. A rotation stamped before activation is not needed. Ordinary subscription dispatch, the control arm, PR review, CI and merge are never held.
- **Report.** `rmd benchmark-paid-pilot report --pilot <id> [--case-files <snapshot.json>]` writes a private report with no public export. It is split by task class and arm, and gives verified completion, human effort (unavailable until an independent receipt exists), recovery, later defects (censored until the maturity window closes), cash estimates and notional cost kept apart, assignment denominators, missingness, censoring, the interval, the pinned stack revisions and an `eval-card-v1` card. No conclusion is drawn before the stopping rule. A report that cannot read its sources keeps the last dated report, marks it `stale` with the reason, and names a repair follow-up.
- **Not yet wired.** The dispatcher does not yet route a pilot task to the paid arm's model. The admission seam and the report exist, but production routing policy is unchanged. Connecting the seam to dispatch is separate, reviewed work.
- **Pause and resume.** `rmd benchmark-paid-pilot pause --pilot <id> [--note <text>]` and `resume --pilot <id>` append to `<state>/benchmark-paid-pilot-v1.<pilot>.controls.ndjson`. The file is append-only and its newest entry wins. `paidPilotArmAdmission` reads it: a pause holds the paid arm and stops new pairs, and in-flight attempts finish. An unreadable or malformed control file holds the paid arm too.

## Paired design: `design: "paired"` (W1-T4625)

Comparing two unpaired arms pays for the difference in difficulty between tasks. The paired design removes it by running both arms on the same task (`src/lib/paired-trial.ts`). It changes no production routing.

- **Protocol.** A request with `design: "paired"` adds `paired: { samplingRate, maxPairs, shadow }`, and all three are required. The rate is in (0, 1]. The pair cap is at most 500, and it is a backstop behind the $100 cash ceiling. `shadow` must be an explicit boolean. The unpaired design stays valid and is the default. In a paired protocol, each population task's `arm` names the arm whose attempt runs first. The uncertainty method is exact McNemar on discordant pairs plus a paired difference with a Wald 95% interval. The stopping rule is the pilot's own fixed horizon.
- **Sampling point.** `runPairedTrial` runs from `runTask` right after normal dispatch admits the task: after the already-merged check, the dependency and linter gates, and the in-flight lock. The call is fire-and-forget. It never throws, and its answer is never read. With no active paired protocol it returns at once and writes nothing. An eligible task is a population task on the implement lane. It is sampled when `sha256(benchmark-paired-sample-v1, seed, taskId)` falls below the rate. That draw is independent of the order draw, so both are stable per task. Every eligible decision is written as a `paired_trial.decision` row with its randomisation receipt: the seed hash, the draw, the rate and the order. A task is paired at most once.
- **Isolation.** Each pair runs two EXTRA side attempts through their own dispatcher seam. Each attempt runs on its pinned provider, model and effort, with the pilot's pinned revisions. The contract is a fresh detached worktree with nothing pushed, no PR and nothing merged. A result that reports a pushed ref or a PR URL is an isolation breach, and that pair is unmeasurable. The normal dispatch of the same task keeps its own model, routing and spawn, and it is the only path that can produce a merged change.
- **Grading.** Both heads are graded by the task's visible and holdout acceptance criteria. Grading uses the reviewer's own `parseWhitelistedProof` and `execWhitelistedProof`, and folds the results with `scoreCorpusReplay`'s rule: any fail fails, any unmeasurable is unmeasurable, and only all passing passes. A pair with an unmeasurable side (no head, a crashed attempt, a proof that cannot execute, a grader failure, a breach) is `unmeasurable`. It is never a win or a loss for either arm. The second attempt is not run once the first is unmeasurable, so no cash is spent on a pair that cannot count.
- **Stack pins.** Each side attempt's `paired_trial.spawn` row carries a `benchmark-run-v1` assignment receipt. Its prompt, tool, scorer and environment revisions come from the protocol's pinned revisions with `source: "trial-manifest"`. Its harness revision is the one the executing process attests. A harness off the protocol's pin is recorded as a stack deviation on the spawn and pair rows, and the report counts it.
- **Cash.** Cash counts only the paired paid attempt's API-billed estimate (`paired_trial.attempt`), under W1-T4603's per-call accounting. The control attempt is notional. An API-billed control attempt is treated as ambiguous, which pauses the pilot, and never counts as cash. Normal dispatch rows are not pilot spend. The paid spawn marker is written before the spawn. A marker with no receipt is a missing cost receipt, and it pauses the next pair, so paid attempts run one at a time across processes. Within one process only one live pair runs at a time. Admission is re-read immediately before every paid spawn, not only at sampling time.
- **Shadow mode.** A protocol with `paired.shadow: true` records every decision the sampler would take (whether it sampled, whether it would admit, and the order) and never spawns or spends. A shadow protocol blocks only another shadow, so the operator can shadow for a day and then activate the live protocol under a new pilot id.
- **Report.** `rmd benchmark-paid-pilot report --pilot <id>` on a paired protocol writes a `benchmark-paired-pilot-v1` report. It gives the shadow and live decisions (eligible, sampled, admitted, refusals by reason, order balance with an exact binomial p-value), the pairs with each attempt's served model, billing and cost, cash from paid attempts only, stack deviations, the McNemar counts and exact p-value, the paired difference and interval, the stopping rule, and an `eval-card-v1` of kind `paired-pilot`. No winner is declared until the stopping rule is met and the interval excludes zero.
- **Not yet wired: the sandboxed attempt dispatcher.** In production, `runTask` passes no `dispatchAttempt`, so a sampled live pair is refused as `attempt-dispatch-not-wired` and spawns nothing. Shadow mode is fully wired. The remaining work is a dispatcher that creates a detached worktree at the task's base and spawns the pinned worker with the receipt's stack evidence, without pushing. It also needs a grader run for `unit test:` proofs in that worktree.

## Field trials from our own flow: `field-trials-flow-v1`

`rmd field-trials` (W1-T4574, `src/lib/field-trials-flow.ts` and `src/lib/field-trials-github.ts`) is an operator-invoked, resumable snapshot over the fleet's own history. It is observational: it ranks no model and claims no causal benefit. Causal claims wait for the A/A then A/B ladder above.

- **Inputs.** For each source repository (core, site, console by default), it reads the audited three-form ledger union where that ledger is on the host, and the repository's GitHub history. GitHub is read through one injectable page seam: pull requests, main commits and deployments are swept newest first and paged. Each PR also gets reviews, commits and first-commit check runs. A sweep that stops on a failed page or the page budget records its resume page. Only a completed sweep advances its watermark. An edited or still-open PR is re-read. A rerun is the latest attempt of a check name, never a new PR. Cursors keep as-of time, pages read and the reason for any partial read.
- **Linking.** A PR joins a plan task by the `Remudero-Task:` trailer, the `run-<task>-<digits>` branch and the ledger's `pr.opened` URL, each counted separately. Disagreeing paths make the PR ambiguous. Unmatched PRs, ledger PRs GitHub never returned, and GitHub-only tasks are all counted.
- **Families,** by source, ISO week and task class:
  1. Model adoption per instance and day. Requested, selected and served models are tallied separately, and a missing served model reads `no-attempt` or `not-recorded`. Per model, it records source merge (the booted head's commit time), runtime boot, and first selected and first served exposure.
  2. The funnel: eligible → assigned → worker → PR → review → merge → deployment → verified, with missing-join, censored and human-touch counts at every stage.
  3. PR repair signals: first-pass CI, change-request rounds, repair commits, fix dispatches, reverts, and same-task follow-up merges within a 14-day window. Correctness buckets are `adverse-signal`, `window-immature`, `no-adverse-signal-in-window` and `unknown`, and a green check moves no PR between them. Incidents are unavailable.
  4. Claim → PR, merge and deploy times as Kaplan-Meier quantiles, with open work censored and closed-unmerged work a competing outcome. DORA commit-to-deploy lead time is kept apart, alongside retries, self-repair and escalation.
  5. Learning-loop yield: gardener proposals to accepted, declined, open or unknown, plus credit and debit judgements and follow-up reverts. Human effort is unavailable, never zero.
- **Evidence rules.** A deployment is a GitHub deployment whose newest status is `success`, or a daemon boot at or after the merge commit on main. A merge alone is never one. Verification comes only from W1-T4608's case-file join.
- **Incremental replay.** Partitions carry input hashes, so a late page or a ledger repair rebuilds only the partitions it touches.
- **Privacy.** The snapshot is private. A release needs a `field-trials-consent-v1` file granting `aggregate-opt-in` or `public-benchmark` for a repository. Releases use salted, rotatable pseudonyms and withhold cells and counts below five, with complementary withholding. Stage denominators are omitted because they equal an earlier stage's count. A release is refused if any private join key appears. It is a dated `candidate-unreviewed` file in a revocable manifest. Withdrawing consent or running `--revoke` withdraws it. A failed refresh keeps the last known good release and prints `field_trials.refresh_failed`. Nothing is scheduled, gated, routed, paid for or published.

Deferred from W1-T4574: a scheduled cadence and gardener consumption of the failure event; site import; per-PR pagination beyond 100 reviews, commits or check runs (flagged `truncated`); an incident source; human-effort estimates; W1-T4618 task-shape strata beyond task class; and public source links beyond a consent file's `publicSourceUrl`.

## Publication contract and rollout

The site currently accepts no production `field-trials-v1` artifact. The first real release needs an approved public opt-in corpus, a frozen scoring and interval method, two comparable arms, assignment audit, denominators/coverage, uncertainty, date and provenance, a privacy review, and a revocation path. Static release data are reviewed as source; the marketing site never queries a private daemon. Release charts have an accessible table with the same values and a short description of the trend, following [W3C guidance on complex charts](https://www.w3.org/WAI/tutorials/images/complex/). Distinguish experimental estimates from observational fleet trends and keep a visible change log for rescored, superseded, or withdrawn results.

The next implementation slices are deliberately independent: (1) `benchmark-run-v1` metadata and falsifiers for missing cost/outcome/served-model fields; (2) deterministic local cohort projection with lineage, late-data replay and resource accounting; (3) A/A allocation and integrity report on public fixtures; (4) insight-gardener proposals on derived cohorts; (5) reviewed aggregate release builder and site integration. No slice adds a new PR-stopping check. Existing routing and archives continue to work if the benchmark projection is unavailable. Publish a graph only after the relevant cohort has an actual release receipt.
